# Rust 阶段 2：Host 骨架与分域迁移（rust-unified-host.md 子 spec）

> 状态：立项 · 2026-10-14
> 父计划：`rust-unified-host.md` §阶段 2；前置：阶段 1（子 spec `rust-u1-runtime-lib.md`，验收报告 `docs/reports/rust-u1-runtime-library-2026-10-14.md`）
> 参考实现：ZCode-rs `apps/zcode-cli-rust`（Host 与服务分层）、`apps/zcode-host`（若同构即对照）；对标仓库质量结论见 `docs/reports/rust-impl-quality-comparison-2026-10-14.md`

## 1. 目标与边界

把桌面 Host（现 `packages/desktop` 的 TS Host + 每 workspace 一个 Rust CLI 子进程）迁移为 `apps/escode-host`（Rust）：一个 App 一个 Host 进程，window→Host 经 attachment 接入，runtime 以 embedded 为默认（阶段 1 已具备 `embed::spawn`），child 模式保留作差分/回退/故障隔离。

本阶段分两个可交付批次：

- **u2a 骨架与通路**（先行，本文详述）：Cargo workspace 结构、基础设施（TaskScope 复用、有界通道、原子写、Gateway、control、capability 握手）、Host 服务契约清单与 `--check`、dev 开关与回退链，全部带单测/进程内测试。
- **u2b 分域迁移**（9 个服务域按优先序逐个交付，每域一份子 spec + 差分与 E2E 证据）：settings → workspace → sessions/tasks → providers/account → extensions → automation → remote + runtime-link。

### 1.1 Host 作用域决策（本阶段确认项）

父计划 §2 的边界变更：**现文档为 window-scoped Local Host，目标形态是一个 App 一个 Host（所有窗口经 attachment 接入）**。u2 确认采用目标形态，理由：

- 一份实例表/代次/订阅归属才能真正共享 runtime 实例与缓存（父计划阶段 4「跨实例共享缓存」的前提）；
- 无窗口调度（cron）必须有独立于窗口的宿主（父计划 §2 状态所有者：Host 拥有调度）；
- 窗口关闭不应终止 runtime（attachment 断开 ≠ Host 停止）。

实施时（u2b 落地批次）同步更新 `AGENTS.md` 的进程与协议段落与相关 spec；在此之前 AGENTS.md 描述仍与当前代码一致，不改。

### 1.2 命名

现有 `apps/escode-cli-rust/crates/host` 是 CLI 的**配置/路径 adapter**（workspace 路径、env、凭证、进程组），与新 Host 概念重名。u2 内将其更名 `crates/support`（或 `crates/kit`），一次性改名 + 全仓引用更新；各子 spec 引用新名。

## 2. 工作区结构

对标三 workspace（Host 不拖 CLI 编译与依赖）：

```
apps/escode-host/
  Cargo.toml                 # 独立 workspace（phase 2 起点：仅本 workspace 的 crate）
  crates/
    host-core/               # 基础设施：TaskScope（复用 core-api::scope）、有界通道、原子写、进程回收
    host-gateway/            # 连接注册表、到达序 lane、出站队列、capability 握手、RPC 路由
    host-control/            # Main↔Host stdio 控制（日志与控制同一有序队列）
    host-services/           # 服务域聚合（u2b 起按域拆分：settings/workspace/sessions/...）
    host-proto/              # Host↔Renderer 协议类型（从 packages/shared 生成/校验，L1 契约）
```

共享基础：**直接复用阶段 1 的 `escode-cli-core-api`**（`env::EnvSnapshot`、`scope::Spawner`、`catch_panic`）而不是复制——`apps/escode-host` 以 path 依赖引用 `apps/escode-cli-rust/crates/core-api`。这是 U1 库化的直接红利，也是「基础 crate」优先序第 1 项的落地方式（复用，非重写）。

## 3. 基础设施（u2a 交付物与验收）

### 3.1 TaskScope

复用 `core_api::scope::Spawner`：唯一 spawn 入口、panic sink 上报、`running()` 残余清单、`drain(grace)` 宽限、实例 env 传播。Host 侧每个服务域各持一个 Spawner（父子 scope 语义：域结束时中止本域任务）。验收：Host 收口后各域 `running()` 为空。

### 3.2 有界通道（每队列写明溢出策略）

| 队列                                  | 常量与构造点                                                                                                                                                                   | 容量                                       | 溢出策略                                                                                                                                                                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RPC 连接出站（Host→Renderer 帧）      | `host-rpc/src/connection.rs` `HIGH_WATER`/`LOW_WATER`/`HARD_LIMIT`；`connection::run` 构造（无界通道 + 字节计数）                                                              | 字节水位高 8 MiB / 低 2 MiB，硬上限 64 MiB | 不丢帧：高水位 → 连接 `saturated`（V4 面转发 `v4/connection/flow`，runtime 暂停投递、恢复时补快照），低水位 → `drained`；超硬上限关闭连接（fail closed）。2026-10-15 前该队列不存在（读循环内同步写）                           |
| runtime→Host 帧扇出（每订阅者）       | `host-runtime/src/instance.rs` `SUBSCRIBER_CAPACITY`/`EARLY_FRAMES_CAPACITY`；`Instance::subscribe` 构造                                                                       | 4096 行；首个订阅者前缓冲 1024 行          | 不静默丢帧：订阅者满即摘除并置 `lagged`（接收端可观测，由订阅方让该连接的订阅失效、客户端 resync）；早期缓冲溢出时首个订阅者一开始即 lagged。2026-10-15 前实现为 `try_send` 满即静默丢弃，与本表原文「满时阻塞」不符（评审 A2） |
| host-surface 连接出站（V4 NDJSON 面） | `host-surface/src/lib.rs` `OUTBOUND_CAPACITY`；`Gateway::register` 经 `host-core::bounded::channel("gateway-outbound", …, DropReconstructible)` 构造；实例帧泵 `try_send` 投递 | 256 帧                                     | 满即丢该连接的这一帧（可重建流，由快照恢复补齐），不阻塞帧泵                                                                                                                                                                    |
| Host 控制队列（控制消息 + 日志批次）  | `src/control.rs` `CONTROL_QUEUE_CAPACITY`；`ControlWriter::channel` 构造                                                                                                       | 1024 条                                    | 控制消息必达（队满时等待）；**日志批次队满时任何级别都可能丢**，按写者计数（`ControlWriter::dropped_logs()`）与进程计数（`logging::dropped_batches()`），并镜像到 stderr（Main 以 `stdio: inherit` 接收）                       |

2026-10-18 M2 订正（`rust-u2-host-resilience.md` §6）：

- 删除原表「Gateway 入站（Renderer→Host RPC）256 条，触发背压」一行：真实 RPC 路径（`host-rpc`）不设入站队列，读循环登记后立即交给独立任务，入站压力由 WebSocket/TCP 接收窗口承担；`host-gateway` 也没有入站队列，它只为 `host-surface` 建出站 lane。
- Host 日志原写「丢弃最低级别并计数（warn 起不丢）」，与实现不符（`ControlWriter::log` 队满时任何级别都丢）。取「队满时任何级别都可能丢，并计数」，理由：日志 sink 在同步上下文（含持锁路径）里被调用，必须非阻塞；warn 起不丢只能阻塞调用方或另开无界旁路，前者拖住业务路径、后者破坏有界性；丢弃只发生在 1024 条积压时，stderr 镜像仍保留内容。

每个队列的容量与策略在代码常量处注释引用本表；`host-core` 提供 `bounded::channel(name, capacity, policy)` 统一构造与指标（队列深度、丢弃数），目前只有 host-surface 出站经它构造，其余三个队列的计数在各自类型上（字节计数、`lagged`、`dropped_logs`）。

### 3.3 原子写与进程回收

- 原子写：rename 重试（EPERM/EBUSY/Win32 32/33）+ 父目录 fsync（质量报告 §5 给 Z 更好的落点；u2a 内实现并单测）。
- 进程回收：复用 `escode-cli-host` 的 process_group / process_tree 三补丁（阶段 0 已完成），Host 侧不再自建。

### 3.4 Gateway（连接注册表与到达序 lane）

```
Renderer ──WS──► accept ──► 登记（同步，决定 lane 位置）──► 每连接 lane（单写者）
                                    │
                                    ├─ 请求 → RPC 路由（Host 服务 / runtime 会话）
                                    └─ 事件 → 订阅投递（topic 归属由 runtime 拥有）
```

关键规则（父计划 §2 与质量报告 §7）：

- **登记必须在请求到达时同步完成**：连接（或请求）进入 lane 的顺序由 accept/read 的到达序决定，不能依赖任务调度顺序——否则并发请求的应答顺序漂移。
- 每连接一个写者：出站帧按 lane 顺序写出，控制帧优先但不插队数据帧的内部顺序。
- **适用范围（2026-10-18 M2 订正）**：Gateway 的同步取号（`register`，lane 序 = 连接到达序）只用于 `host-surface`（V4 NDJSON 传输面）。Renderer 的真实 RPC 路径（`host-rpc`，`@escode/rpc` over WebSocket）不经过 Gateway lane：它保证的是**每连接**的登记序 = 到达序（读循环按到达顺序同步调用处理函数，TS `ChannelServer` 同构），执行并发、响应按完成顺序发出并按 id 关联，跨连接不保证全局顺序。细则与测试见 `rust-u2-host-resilience.md` §5（`host-rpc/tests/rpc_order.rs`）。M2 之前 `host-rpc` 在独立任务里才调用处理函数，同一连接的登记序不确定，已修复。
- capability 握手：连接建立即协商（客户端 capabilities ∩ Host 支持的 method 集），未实现成员立即回 `NotImplemented`（Renderer 不挂起，缺口显式可见）。

### 3.5 Main↔Host control

stdio 上单条有序队列：日志与控制消息共用一条写者（避免交错破坏协议）；控制消息 typed（`ControlMessage` enum：`WindowAttach/Detach`、`HostReady`、`Shutdown`、`LogBatch`），错误用结构化 code。

## 4. 服务契约清单（L1 门禁）

`host-proto` 导出 channel/method 清单（单一来源），`--check` 与各服务实现的存在性对账：

- 清单与源码不一致即失败（生成器 + `--check`，接入 `pnpm check:escode-host`）；
- 未实现成员在 Gateway 立即回 `NotImplemented`，并出现在契约清单的 `pending` 分组（缺口显式可见，不静默 404）；
- 契约清单是阶段 3 前 golden freeze 的输入之一。

## 5. 分域迁移（u2b 优先序与每域验收模板）

每域开工前按父计划子 spec 约定写 `docs/specs/rust-u2<序号>-<域>.md`。

## 6. dev 开关与回退

- 单一开关（env `ESCODE_RUST_HOST=1`，dev 默认关；阶段 3 翻转默认）同时决定 Host 实现；开关只影响装配，不影响任何协议语义。
- child 模式：`runtime-link = child` 时 Host 以 `app-server --stdio` 拉起 CLI 子进程（阶段 1 之前的形态），用于差分、回退与故障隔离。
- 回退矩阵与演练沿用 `rust-release-rollback.md`（阶段 3 扩展 installed 四平台）。

契约清单已与源码对账（`host-rpc/tests/contract.rs`，3 例）：各 channel 的**方法表就是分派来源**（`Channel{name, methods: Vec<(&str, MethodHandler)>}`，`session::respond` 只查表；表外方法回显式缺口 `Host does not implement \`{channel}.{method}\` yet`），因此对账是双向机器校验而非人工核对：

1. `source_method_table_matches_implemented_entries`：清单标 `Implemented` 的 (channel, method) 必须在真实方法表里出现（漏登 → 渲染器永远拿不到，报错列出差集），且 `MethodHandler` 分派能命中；
2. `pending_entries_are_not_implemented`：清单标 `Pending` 的不能在方法表里（否则缺口会静默变成可用）；
3. `every_rpc_channel_is_registered`：`host-proto` 登记的 channel 集合 ⊇ 组合根实际注册的 channel。

`control`/`settings` 通道另由 `host-proto` 的 `control_inventory_matches_the_protocol_enum` 漂移测试保证与 `ControlMessage::kind()` 集合一致（新增消息不登记即失败）。负向验证：把 `file.readdir` 从 `Pending` 翻成 `Implemented` 后 `source_method_table_matches_implemented_entries` 立即失败并列出 `[("file", "readdir")]`，改回即恢复。

**`rpcListen.runtimeEnv`（审计 A16a，2026-10-15）**：可选的 `{name: value}` 映射，由 Main 合成（`desktopRuntimeEnv.ts: buildRustHostRuntimeEnv`：Node Host 进程同源的基础 env，去掉 OTLP 连接配置——它只允许在启动 Agent 时短暂注入，不能进入会被工具/MCP 子进程继承的实例快照）。Host 把它原样作为每个实例 `RuntimeOptions.env` 的底，再叠加 `ESCODE_WORKSPACE_IDENTITY`（由 workspace 描述决定，优先于 Main 的同名项）。Host 不从自己的进程 env 推断这些业务事实。缺省（旧版 Main）行为不变。provider 配置文件路径与插件宿主入口尚未下发，见审计 A16b。

**Host 日志出口接齐 §3.2/§3.5（2026-10-16）**：此前 §3.2 的「Host 日志」只有骨架——`main.rs` 的 `ControlLoop` 把控制消息**直接写 stdout**（`ControlWriter` 的单队列此前只被单测用到），host-rpc / host-services 的日志走 `eprintln!`（stderr，绕过控制队列），且 Main 侧 `rustHostBridge` 把 `logBatch` 当无关帧跳过（`nextMatching` 上限 50 帧）。现在三段接齐：

- **Host 侧**：`host-control::logging` 是进程级 sink（`Arc<dyn Fn(LogBatch)>`，与 CLI runtime `file_log` 同形）；服务域（host-rpc / host-services / host-surface / host-runtime）只投递 `(scope, level, lines)`，不持有控制通道句柄。`main.rs` 装配时 `install_sink(control.log_sink())`；收口时 `ControlLoop::close()` **先 `release_sink()` 再关队列**——sink 持有写句柄克隆，不释放则队列永不关闭（进程等泵退出会挂死，已加回归单测 `logging::tests::releasing_the_sink_closes_the_control_queue`）。未装 sink / 队列满时回退 stderr，诊断不丢。
- **出口**：`ControlLoop` 改为 `ControlWriter` 单队列（容量 1024）+ 一个泵任务串行写 stdout。队满时控制消息等待、日志从结构化出口丢弃并计数（`logging::dropped_batches()`）且镜像 stderr——满足 §3.2「队满时任何级别都可能丢，并计数」的可见性要求（M2 起另有按写者计数 `ControlWriter::dropped_logs()`）。
- **Main 侧**：`startRustHost.onLogBatch` 校验并消费 `logBatch`（scope/level/lines），经 `rustHostManager` 落到 Main logger；`logBatch` 不再进握手队列。
- **代码约定**：Host 各 crate 不再用 `eprintln!` 记业务日志（`logging` 的 stderr 兜底除外）；级别照 AGENTS.md（`warn` 可恢复、`error` 不可恢复），scope 取域名（`window-controller`/`task-index`/`file-watcher`/`git`/…）。
