# Rust vs Node：真实模型服务延迟（2026-09-25）

补齐 `rust-perf-2026-09-24.md`「性能验收仍缺什么」中的「真实供应商」与「p95/p99」两项。

## 方法

- 用例：`packages/services/tests/zcode-cli-rust-real-provider-bench.test.ts`（默认跳过；
  `ZCODE_BENCH_PROVIDER_ID=<~/.zcode/v2/config.json 中的 provider id>` 启用，`ZCODE_BENCH_ROUNDS` 控制轮数）。
- 模型服务：用户指定的自建 DeepSeek（`deepseek-v4-flash`，OpenAI 兼容，局域网 vLLM；服务端自报 TTFT 约 250ms）。
- 两侧使用同一份 personal provider 配置，经真实 App 协议驱动；Node 与 Rust **交替**执行 20 轮以抵消服务端漂移。
- 每轮新起一个进程：计「进程启动到会话创建完成」、同一会话**首轮**（冷）与**第二轮**（热）从发出 `sendText`
  到出现本轮首段助手文本、到本轮完成的时间。只认本轮新建的行（两侧都会重发上一轮的行）。
- 请求很短（"Reply with exactly one word"），回复通常一个分片，因此首段文本与完成时间接近。
- 代理：开发机设置了 HTTP(S) 代理，会把局域网请求转走（实测 503）；用例把供应商主机加入两侧的
  `NO_PROXY`/`ZCODE_NO_PROXY`。
- 环境：Windows 11 x64；Node 为随包 `zcode.cjs`；**Rust 为 GNU 目标的 debug 构建**（测试夹具默认），
  release 构建只会更快，因此 Rust 数字偏保守。

## 结果（毫秒，n=20；p99 在 n=20 时即最大值）

| 指标             | Node p50 / p95 / p99 | Rust p50 / p95 / p99 |
| ---------------- | -------------------- | -------------------- |
| 进程 + 会话就绪  | 2017 / 2136 / 2209   | 464 / 498 / 502      |
| 冷首轮：首段文本 | 3678 / 3751 / 3756   | 327 / 402 / 409      |
| 冷首轮：完成     | 3678 / 3764 / 3777   | 333 / 409 / 432      |
| 热轮：首段文本   | 537 / 555 / 557      | 297 / 313 / 675      |
| 热轮：完成       | 537 / 555 / 557      | 303 / 318 / 680      |

40/40 次均得到有效回复，两侧 schema 校验均无错误。

## 怎么读

- 热轮 Rust 约 300ms，接近服务端自报 TTFT（约 250ms），说明运行时自身开销很小；Node 热轮约 540ms，
  多出约 240ms 运行时开销。
- 冷首轮差距最大（约 3.7s → 0.33s）：Node 在进程内首次请求前的准备成本很高，Rust 基本没有。
- Rust 热轮的 p99（675ms）是 20 次中的单个离群值，其余均在 320ms 内；样本量不足以区分运行时与服务端抖动。
- 结论边界：这是**一个**自建局域网服务、极短请求、20 轮的结果。公网供应商（网络延迟更大、占比更高）、
  长回复流式、长历史与工具调用场景未覆盖；三平台原生与 release 构建也未在本次测量中。
