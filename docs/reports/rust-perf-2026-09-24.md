# Rust vs Node runtime 性能实测（2026-09-24）

## 方法与口径

- 工具：仓库自带 `scripts/bench-zcode-cli-node-rust.mjs`（同一 workload 串行跑两侧，交替释放）。
- workload：本地 SSE provider，8 个 turn × 256 chunk（每 chunk 25B），context window 256k。
- 采样：每 25ms 采一次 RSS，记录启动耗时、空闲 RSS、峰值 RSS、墙钟、CPU 秒数。
- 重复：5 次配对运行，下表取中位数与范围。
- 环境：WSL2 Ubuntu（Linux x64）、Intel Xeon Gold 5218R @2.10GHz、Node v22.22.1；
  Rust 侧为 `cargo build --release` 的 GNU/Linux 产物（`1c81d0d3…`，sha256 见 JSON）。

**为什么在 Linux 跑**：该 harness 用 `ps -o rss=,time=` 采样，Windows 的 `ps` 不支持 `-o`，
因此无法在 Windows 原生运行；两侧都在同一 WSL 环境、同一 Node、同一机器上跑，A/B 可比。

## 结果

| 指标          | Node                 | Rust                                   | 倍数  |
| ------------- | -------------------- | -------------------------------------- | ----- |
| 启动耗时      | 3305 ms（3287–4177） | **15.7 ms**（14.3–25.0）               | ~210× |
| 空闲 RSS      | 339 MiB（331–334）   | **11.3 MiB**（11.3–11.6）              | ~30×  |
| 峰值 RSS      | 394 MiB（384–385）   | **19.5 MiB**（19.3–19.7）              | ~20×  |
| workload 墙钟 | 15.9 s（15.5–17.8）  | **0.18 s**（0.178–0.191）              | ~87×  |
| CPU 秒数      | 5–6 s                | 0 s（`ps -o time=` 精度为 1s，即 <1s） | —     |

原始 JSON（每次重复的完整指标）在运行目录 `bench-out/`。

## 怎么读这些数字

- 这个 workload 衡量的是**运行时自身**的协议与循环开销（本地 provider、无真实网络），
  因此 87× 的墙钟差主要来自 Node 侧每 turn 的固定开销，而不是模型调用。
- 启动与内存的差距更贴近用户体验：Rust 进程 15ms 级别启动、11 MiB 空闲驻留，
  对「多个窗口各自一个 Local Host」的桌面形态意义明确。
- 不能据此宣称「真实对话更快」：供应商延迟、长历史、工具执行都不在本口径内。

## 与既有口径的关系

`docs/specs/rust-runtime-performance.md` 记录的 2026-09-22 数字（首段降低 36%–38%、12 会话空闲 RSS 降低 26.6%、
大页查询 312→5.3ms）来自另一套 harness（`bench-zcode-cli-rust-suite.mjs` /
`bench-zcode-cli-rust-session-memory.mjs`），比较的是 Rust 新旧版本而非 Node/Rust。两者互补，不互相替代。

本次新增可用于性能验收的证据：

1. 本报告（Node vs Rust 的启动/内存/协议吞吐，5 次配对，Linux）。
2. Windows 上首个模型请求 1830ms → 35ms（prompt 快照不再 spawn PowerShell，见 rust-windows-parity.md）。
3. 120 会话 + 1.5 MiB 附件的 TS 导入约 0.88s（`zcode-cli-rust-migration-scale.test.ts`）。

## 性能验收仍缺什么

- **三平台原生**：Windows 原生与 macOS 未跑同一 harness（Windows 需先让采样走 Windows API；
  macOS 需 mac 机器）。
- **真实供应商**：本地 SSE 不能代表真实首 token 与流式长尾。
- **大活跃历史**：单会话大历史的分页/投影延迟未测。
- **流式稳定阶段 RPC 长尾**：仅测了平均吞吐，未测 p95/p99。
- 结论不得超出上述范围：目前只能说「运行时自身开销与驻留明显更低」，不能说「端到端更快」。
